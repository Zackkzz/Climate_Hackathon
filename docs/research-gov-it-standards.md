## (b) The 15 application-level controls to build this weekend (most important first)

1. Per-organisation data isolation and role-based access (R01): a council user can never read a landlord's or tenant's data outside their programme; test it.
2. Authentication hardened: Argon2id/bcrypt hashing, login throttling, lockout, no default accounts, accessible login (WCAG 3.3.8) (R34, R21).
3. MFA (TOTP or passkey) for every account that can see tenant data, plus an OIDC/SAML SSO stub for Entra ID for council/agency staff (R02).
4. Append-only audit log of who viewed, exported, changed or consented to anything involving NMIs, names, readings or ledgers; viewable by an admin and exportable (R08).
5. Consent records for every NMI/data pull: who consented, scope, purpose, timestamp, expiry, withdrawal (R29, R28, R24).
6. Data minimisation and masking: NMIs and addresses masked by default, reveal on demand and logged; no health data collected (R24, R27, R29).
7. Encryption: TLS 1.2+ only with HSTS, encrypted-at-rest database and backups, secrets in environment config not code (R11, R33).
8. Web hardening: CSP, X-Content-Type-Options, frame-ancestors/X-Frame-Options, Referrer-Policy, Secure/HttpOnly/SameSite cookies, CSRF protection (R05, R33).
9. Input validation, parameterised queries and output encoding; file upload (bill photos) type and size checks, malware-safe handling (R33).
10. Session management: short idle timeout, absolute timeout, rotation on login, full invalidation on logout (R34).
11. Data export and deletion: a tenant or council can export their records in CSV/JSON, and a retention/delete function with a documented schedule (R12, R31).
12. Accessibility to WCAG 2.2 AA: contrast 4.5:1 and 3:1 non-text, visible and unobscured focus, 24 px targets, reflow at 320 px, labelled forms with text errors, aria-live status messages, full keyboard operation (R16 to R22).
13. Chart accessibility: every chart has a data table alternative, uses patterns/labels and not colour alone (R22, R17).
14. Security-relevant logging and alerting hooks plus a breach-response page/runbook with a notification template (24-hour supplier-to-agency clock) (R09, R25).
15. Dependency hygiene: lockfile, automated vulnerability scan in CI, a published SECURITY.md contact, and a short trust page listing hosting region (Australia), subprocessors and support location (R04, R13, R32).

Use Public Sans with an Arial fallback and NSW Design System tokens where cheap (R23); it is recommended, not required.

## (c) What a weekend prototype cannot honestly claim

- ISO 27001 certification, SOC 2 report, or IRAP assessment of Meterwise (it can only say it is hosted on an IRAP-assessed provider region, if true).
- Essential Eight maturity assessment or attestation: the policy's E8 duties fall on agencies; Meterwise can say it was designed to align with ML1 application-level strategies and which are not applicable.
- A penetration test by an independent party; a self-run automated scan is not a pen test.
- A formal WCAG 2.2 AA conformance report or VPAT/ACR from an accredited auditor; it can claim "built to target WCAG 2.2 AA, self-tested with axe and manual keyboard checks".
- Compliance with the PPIP Act, MNDB scheme, State Records Act, Privacy Act or CDR; it can only say it is designed to support these.
- Consumer Data Right accreditation or AEMO/MSATS participant status; any real NMI data access through a retailer or distributor needs agreements and customer authority that do not exist yet. Demo data must be synthetic and labelled as such.
- Tested RPO/RTO, restored backups, a rehearsed incident response, or 24/7 monitoring.
- Any statement that real tenant data is held; the prototype should use synthetic records.
